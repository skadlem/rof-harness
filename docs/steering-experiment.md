# Steering feasibility experiment

**Status: void — the premise was a workspace-seeding bug, not a model habit (2026-11-06).**

Registered before new model calls; voided 2026-11-06: every in-container run before that date seeded `/app` from `<task>/environment` (the Docker build context) instead of the image's `/app`. On `custom-memory-heap-crash` those differ, and the verifier md5-checks and compiles `/app/main.cpp`, so each seeded run was a structurally impossible 0/6 and the recorded read streaks were reads of a build context. This triggers the campaign's own stop rule ("a verifier integrity problem appears"): no pair from an earlier campaign is eligible, no treatment efficiency can be inferred, and the threshold and directive are unvalidated on a correct workspace. The paused `dphn-steer` arm stays diagnostic only and must not be pooled.

Chosen, unvalidated design: a frozen new binary with the 300,000 gross-token / 60-step / 120-action recipe in both arms, one-shot directive after six consecutive successful `view`/`search` results and before the first successful `edit`/`write`, off by default and separate from `--steer on|off`. Threshold was picked after inspecting historical traces — allowlist-control heap rows had maximum read streaks 10 and 21, query-optimize controls 1 and 4, solved log-summary controls 2 (measured 2026-11-03, local `rof-steer-trace-check.py` scanner, `.local/share/rof-tb/work/analysis-grade-check-2026-11-03/`) — and does not validate its efficacy.
