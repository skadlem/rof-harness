# Full TUI vision — live, steerable `rof chat`

Date: 2026-09-25. Status: design target; **not implemented by this document**.

## Goal

Turn `rof chat` into a pi/hermes/claude-code-class terminal workspace for one active `rof` run. The user should be able to watch model and tool work arrive, keep typing while a run is active, steer the next round or queue the next goal, inspect the working diff and run metrics, use the existing slash-command registry, and reopen a recorded JSONL trace for post-mortem inspection.

The defining property is continuity: live mode and replay are two inputs to the same event-to-state reducer and the same pure Ratatui view. The TUI is a workspace, not a progress bar and not a second orchestration system.

## Current baseline (grounded in this repository)

The vision builds on code that already exists; it does not assume a future API.

- `src/main.rs` owns `Setup` and the `chat` loop. It calls `run_live`, receives `LiveOut::Goal`, then awaits `run_goal_text` before returning to the prompt. Consequently the terminal is not accepting composer input while a goal runs.
- `src/tui/run.rs` owns the terminal lifecycle. `run_live_inner` polls `TraceSink::events()` every 33 ms and drains unseen events into `App`; it parses slash commands and owns the current single pending-goal slot. `apply_action` currently applies many session knobs through environment variables between goals. `replay` reads JSONL eagerly and `run_repl`/`pump` run the read-only replay screen.
- `src/tui/app.rs` is the existing single UI-state pattern. It owns transcript strings, counters, composer text, scroll, splash, thinking posture, and input masking. `on_event` is the sole transcript/counter reducer and `draw` consumes state without terminal I/O.
- `src/tui/render.rs` maps the ten current `TraceEvent` variants to transcript lines and folds model/reviewer metrics. Current `LlmClient` completes a request/response; there is no token-delta event type.
- `src/tui/ui.rs` currently splits transcript, status, and composer. `src/tui/theme.rs` supplies named ANSI colors and pane frames; `src/tui/splash.rs` supplies the launch screen.
- `src/tui/cmd.rs` is the existing closed slash registry. `src/tui/auth.rs` is the existing non-secret provider registry plus the 0600 credential store and key verification path.
- `src/obs/trace.rs` defines `TraceEvent` and `TraceSink`. `TraceSink::emit` records events in memory and optionally mirrors one JSON object per line to a trace file; it also maintains O(1) token totals.
- `src/engine/orchestrator.rs` owns the bounded implementer/reviewer round loop and emits ordered model, tool, state, reviewer, budget, skill, and quality events. Planner removal is already reflected here: there is no planner stage to visualize.
- `tests/tui_app.rs` renders `App` with Ratatui `TestBackend`, making layout and reducer behavior testable without a PTY.

The immediate architectural gap is concurrency, not rendering. Today the main async task runs the orchestrator while `src/tui/run.rs` is not running its input pump.

## Target user experience

### Open and orient

`rof chat` opens in the existing alternate-screen fullscreen console. The first key dismisses the splash. At idle, the transcript contains a short prompt and the composer is ready for a goal. A status row identifies terminal mode, active model/provider when known, and the current run state.

### Watch a live run

While a goal is active, the workspace shows an ordered run pane. Model calls, model errors, tool calls, state transitions, reviewer verdicts, budget guards, skill operations, goal-quality notes, and auto-pokes appear as the orchestrator records them. The default transcript stays tailed, but existing scroll controls move the user into history; new events do not yank a scrolled view back to the tail.

“Streaming” in this scope means **ordered event arrival**, not token-by-token model deltas. The current provider contract and trace schema do not carry token deltas. A model or tool step becomes visible when its existing `TraceEvent` is emitted. Adding a delta protocol would be a separate event-contract change, not a hidden part of the TUI.

### Type without leaving the run

The composer remains editable during model and tool work. Enter has two explicit meanings selected by the current busy-input mode:

- `steer` is the default for an active run. The submitted text enters one pending-steer slot and is incorporated before the next implementer round is constructed. It never mutates an in-flight model call or tool invocation.
- `queue` submits one pending goal. It is not started until the current top-level goal reaches a safe boundary and the worker can start the next goal with newly built services.

The latest submit replaces the previous pending item in the corresponding single slot, matching the current one-slot UI and making queue state visible rather than unbounded. Empty submissions do nothing. Composers never claim to be usable when they are not.

### Use commands safely

The existing `src/tui/cmd.rs` registry remains the single source for parsing and help. During a run, commands are handled in two classes:

- View-only commands, such as help, hotkeys, models, trace information, and unknown-command help, may update the view immediately.
- Commands that change execution configuration are accepted by the worker and applied in submission order at a safe round boundary. The view says “pending” until the worker acknowledges application. The current model call is never reconfigured underneath it.

A safe round boundary is the point after one complete implementer/reviewer round and before the next implementer prompt is assembled. At a terminal run boundary, configuration remains pending for the next goal unless the current command is explicitly a queued goal. Configuration changes take effect through services rebuilt for the next round/goal, not by mutating borrowed clients.

`/busy queue` and `/busy steer` select the composer semantics. Help and the status row always show the active mode. This reuses the already parsed `Action::Busy`; the current between-goals message is not sufficient for the target.

### Inspect output

A wide terminal uses a split workspace:

- the transcript is the primary left pane;
- the run pane is the right pane and shows current/recent structured activity;
- a bounded diff pane occupies the lower detail area and shows the current working-tree summary and patch text;
- the status row shows run state plus model-call, token, cost, and review metrics;
- the composer stays docked at the bottom.

A narrow terminal keeps transcript and composer, and makes run and diff full-width views selected from the focus cycle. No information is fetched during draw; panes render snapshots already stored in `App`.

The diff is engine-owned evidence. The UI must not run a second, unsynchronized git command. P3 introduces a bounded diff snapshot at the same harness boundary that owns `TreeService`, then displays that snapshot. When no snapshot exists, the pane says so rather than inventing one.

### Manage BYOK providers

Provider management remains separated into two non-secret/secret stores in `src/tui/auth.rs`:

- the provider registry contains names and base URLs;
- the credential store contains keys at 0600 and is never copied into `App`, traces, status text, completion records, or persistence.

`/providers` is the target list command for built-ins, registry providers, credential presence, and verification status. It supplements, rather than duplicates, the existing `/provider add|list|rm` mutation grammar. `/model provider/model` selects a role binding; it takes effect at the same safe boundary as other configuration commands. Plan A’s provider switching is a prerequisite to the provider/metrics phase.

### Review a recorded run

`rof chat --replay <trace.jsonl>` is the permanent post-mortem view and remains strictly read-only:

- the same `TraceEvent` ingestion, counters, transcript renderer, and workspace view are used;
- the D1 seekable replay contract is retained: `j`/`Down`, `k`/`Up`, `G`, `g`, `/` filter entry, and `q` quit, with `replay i/N [filter]` status;
- malformed or newer lines become the existing unrecognized-event marker and do not affect counters;
- typing never executes a goal, command, tool, or credential action in replay mode;
- replay contains no live-worker channel and therefore cannot mutate a run.

Live JSONL traces and in-memory `TraceSink` events use the same normalization path. A future TUI preference file is not a session store and never becomes replay input.

## Keyboard and focus contract

- Typing edits the composer by default.
- Tab cycles focus through transcript, run, diff, and composer; Shift-Tab reverses the cycle.
- Arrow keys, PageUp/PageDown, Home, and End keep their current transcript scrolling meanings when no dialog or filter is active. A focused scrollable pane consumes them for that pane.
- Enter submits composer text or activates a focused pane action; no pane action in this scope writes repository state.
- `q` is literal composer text when the composer is non-empty. With an empty composer, it arms quit. A second `q`, Esc, or Ctrl-C requests a graceful stop at the next safe boundary; the UI states that the current call is not interruptible.
- Escape closes a transient overlay or filter before it has quit semantics.
- `/` begins replay filtering only in replay mode; in live mode it is the first character of a slash command.
- Resize reflows panes without changing application state.

The implementation should preserve the existing key meanings where they do not conflict with this contract. Focus state, transient overlays, and quit confirmation are `App` state so rendering remains deterministic.

## Architecture

### One event emission seam

Control acknowledgements and diff evidence are trace events, not
live-channel-only events. P1b shipped acks on the live channel alone, which
meant a recorded P1b session replayed with no control history and no diff; the
durable record is the fix for both, and it keeps one emission seam.

- `TraceEvent::Control(ControlAck)` carries the same ordered acknowledgement
  the console already shows. `ControlAck.note` is documented to never carry
  command text or a credential, so the durable copy is safe by construction.
  `LiveEvent::Control` is REMOVED: the sink's live forwarding carries the
  trace event to the console in emission order, which is the same ordering
  guarantee and one path instead of two.
- `TraceEvent::DiffSnapshot` carries the bounded, engine-owned diff evidence
  at the `TreeService` boundary. The UI renders that snapshot and never runs
  its own git query, so the pane cannot disagree with the harness.

`App::on_event` is therefore the only place trace events land, in both live
and replay modes, and a control acknowledgement routes through the same
`on_control_ack` reducer in both.

The orchestrator’s event path remains based on `TraceEvent` and `TraceSink`. P1 adds a worker-to-UI `mpsc` channel beside it. A single emission seam records an event in `TraceSink` and forwards its ordered live notification to the UI; direct call sites that emit to only one of those destinations are forbidden. This prevents a live line and its JSONL record from disagreeing.

The worker-to-UI stream carries three closed categories: an ordered trace event, a round-boundary notice, and a terminal run outcome. `TraceSink` remains the durable/evaluation source and retains its token-total behavior. The channel is a live delivery optimization, not a second event schema and not a replacement for JSONL replay.

### Orchestrator worker future

`src/main.rs` starts the goal in a Tokio worker future and keeps the terminal input pump active in the same process. The worker owns orchestration and service lifetimes. The UI thread never holds or mutates orchestrator state directly.

A second `mpsc` inbox carries UI commands to the worker. The worker drains it only at a safe boundary. This ordering is the central safety property:

1. the worker completes the current model/tool/review round;
2. it drains pending UI commands in submission order;
3. it applies view-independent configuration and guidance, or reports a rejected/unavailable command;
4. it emits a boundary acknowledgement;
5. it starts the next round or returns the terminal outcome.

The inbox is unbounded at the channel so normal observability cannot block a model call; `App` enforces visible single-slot limits for steer text and queued goals. A dropped UI receiver requests a graceful stop rather than aborting an active model/tool call.

### `App` is the single render state

All rendered data lives in `App`: mode, transcript, structured run events, counters, composer, pending steer/goal, busy mode, focus, scroll, pane visibility/size, status, diff snapshot, provider view, and transient help/filter state.

There are two narrow writers:

- the input adapter turns key events into `App` mutations and UI commands;
- the runtime adapter drains worker events/acks into `App`.

`src/tui/ui.rs::draw` remains a function of `&App`. It performs no file, environment, provider, git, event-channel, or clock I/O. `src/tui/render.rs` remains the pure event-to-line/metric reducer. A redraw cannot change behavior or configuration.

This preserves the current TestBackend testing pattern and lets deterministic event sequences exercise live, steering, pane, provider, and replay states.

### Ratatui composition

`src/tui/ui.rs` composes pure pane functions from `App`: transcript, run activity, status, diff, provider table, and composer. Layout and focus selection are state, not terminal queries. A shared bounded collection in `App` prevents unbounded transcript/diff memory; filtering and scrolling operate over those bounded views.

Live and replay use the same pane composition. Differences are expressed as `App` mode/data, not as a second renderer with duplicated formatting.

### Credential boundary

Key capture may be interactive and masked, but key material is passed directly to the auth verification/save path, never inserted into generic `App` notification state or `TraceEvent`. Provider names, bases, model ids, and verify statuses are displayable. A failed change is shown with the provider name and reason but no secret.

## State and event lifecycle

- `Idle`: composer active; transcript and persisted preferences visible; no worker.
- `Running`: worker active; run pane receives ordered events; composer accepts draft text according to the selected busy mode.
- `Boundary`: pending commands drain; `App` shows applied/rejected acknowledgements; steer text is either folded into the next-round record or explicitly reported as not applied.
- `Stopping`: quit/cancel requested; current non-preemptible call continues; next boundary ends the run or starts the queued goal according to the stop policy.
- `Finished`: terminal outcome appears in the transcript/status; composer remains available for a queued next goal.
- `Replay`: trace-derived only; no worker, command dispatch, or credential capture.

Errors are visible state, not a reason to tear down the terminal. Teardown restores raw mode and leaves the alternate screen on every exit path.

## Scope boundaries

### In scope

- A live pane fed by ordered orchestrator events.
- A composer usable during a run, with steer and queue behavior applied at round boundaries.
- Existing slash commands, reused through `src/tui/cmd.rs` and its closed `Action` enum.
- `/providers` and existing BYOK operations, with provider changes applied safely.
- Transcript, run, status, diff, provider, and composer panes.
- Reuse of seekable JSONL replay for post-mortems.
- Built-in themes, slash/provider-model completion, and safe non-secret UI preference persistence.

### Explicit non-goals

- No step-by-step debugger, round rewind, or state mutation from replay.
- No multi-session management, session switching, or concurrent attached runs.
- No remote attachment or browser/mobile client.
- No token-delta protocol; live streaming uses the current completed-event granularity.
- No transcript, composer, credential, or queue persistence.

The non-goals are product boundaries, not deferred silent behavior.

## Verification strategy

- Reducer tests feed real `TraceEvent` values through `App` and assert transcript/counter/state transitions.
- Boundary tests use a deterministic fake worker to prove commands cannot apply before a boundary, drain in order, and produce acknowledgements.
- TestBackend tests cover wide and narrow layouts, every focus target, scrolling, diff/provider tables, masked login, and replay filtering/cursor composition.
- Replay tests use recorded JSONL including malformed/newer lines and prove no worker or command is created.
- Credential tests use override paths and fake verification responses; secrets are never placed in snapshots or assertions.
- Integration tests use the existing stub client and repository workdirs. No network is required for renderer, channel, boundary, or layout verification.
- Each phase runs the full Rust test suite, Clippy with warnings denied, and formatting checks before exit.

## Success criteria

1. A user can type and submit while model/tool work is in flight and can tell whether the submission is pending, applied, or rejected.
2. The live view shows ordered trace events without polling away terminal input or losing the transcript tail.
3. Configuration and guidance change only at safe round boundaries.
4. Transcript, run, status, diff, provider, and composer views render deterministically from `App` at wide and narrow sizes.
5. BYOK secrets remain masked and never enter traces, logs, replay, or persisted preferences.
6. A recorded JSONL trace can be reopened with seek/filter controls and cannot execute anything.
7. `run` and `eval` behavior remains unchanged, and the project’s full checks remain green.
