# Full TUI phased delivery plan

Date: 2026-09-25. Status: phase contract only; **no code is part of this document**.

## Goal and architecture

Deliver the full-TUI vision in `docs/superpowers/specs/2026-09-25-full-tui.md` without changing the safety boundary of orchestration.

The delivery keeps `src/tui/app.rs::App` as the single render state, keeps `src/tui/ui.rs::draw` pure, and keeps `src/tui/render.rs` as the pure trace reducer. `src/main.rs` starts orchestration in a worker future while `src/tui/run.rs` keeps the terminal pump active. A worker-to-UI `mpsc` channel carries ordered trace events, boundary notices, and terminal outcomes; a UI-to-worker `mpsc` inbox carries commands applied only at round boundaries. `src/obs/trace.rs::TraceSink` remains the durable and evaluation source.

The existing slash registry in `src/tui/cmd.rs`, BYOK stores in `src/tui/auth.rs`, and read-only seekable replay contract remain the command, secret, and post-mortem foundations.

## Baseline and dependencies

The following are prerequisites, not work assigned to the four phases:

- Planner removal is complete in `src/engine/orchestrator.rs`; the full TUI has no planner pane or planner stage to restore.
- BYOK provider switching from `docs/superpowers/plans/2026-09-25-byok-providers.md` must be merged and green before P3 begins. The current tree contains its provider registry, per-role client plumbing, provider commands, and masked login, but P3 still treats that plan as a hard dependency.
- D1 seekable replay must be complete before live/replay composition work begins. D2 itself does not implement D1.
- `src/tui/ui.rs`, `src/tui/app.rs`, and `src/tui/run.rs` already provide the console shell; the phases deepen the same module rather than creating a second TUI framework.
- Ratatui, Crossterm, Tokio, and the existing trace/serde stack are available. No phase requires a new dependency.

## Global constraints

- Deliver one phase at a time. A later phase does not begin until the prior phase’s exit criteria pass.
- Preserve the pure-render rule: `draw` never reads files, environment variables, git, clocks, credentials, or channels.
- Preserve ordered event semantics: the live channel and `TraceSink` must be updated through one emission seam.
- Never apply user configuration or guidance inside an in-flight model or tool call.
- Never put API keys, masked key input, or unsanitized auth failures into `TraceEvent`, transcript text, completion history, or preferences.
- Replay remains read-only. A replay view cannot create a worker, submit a goal, dispatch a slash command, or access credentials.
- Keep `run` and `eval` behavior unchanged. New live behavior is opt-in through `rof chat` and its existing replay path.
- Use real `TraceEvent` values in tests and Ratatui `TestBackend` for view assertions. No test may require provider network access.
- Run the full test suite, Clippy with warnings denied, and formatting checks at every phase exit.
- Do not add a step debugger, multi-session UI, remote attachment, token-delta protocol, transcript persistence, or composer persistence.

## P1 — Event channel and live read-only run pane

### Purpose

Make the current run visible while keeping orchestration running on a worker future. This phase proves concurrency and ordered event delivery before any input is allowed to influence the worker.

### Entry criteria

- D1 replay behavior and tests are present and green.
- `src/main.rs` still awaits `run_goal_text` before re-entering the live prompt.
- `src/tui/run.rs::run_live_inner` still consumes `TraceSink::events()` snapshots only while it owns the pump.
- `src/engine/orchestrator.rs` already emits the required ordered `TraceEvent` sequence.
- `src/tui/app.rs` has no live-worker state and `src/tui/ui.rs` shows transcript, status, and composer only.

### Phase scope

- Move the active goal into the worker future while the terminal pump remains owned by `src/tui/run.rs`.
- Add the ordered worker-to-UI event channel and the UI-to-worker command inbox used by later phases.
- Route trace emission, boundary notices, and terminal outcome through one seam so live delivery and `TraceSink` cannot diverge.
- Make `App` the destination for ordered run events, run state, boundary state, and terminal outcome.
- Extend the current transcript/status view with a live activity/run region; preserve the existing tailed/scrolled behavior and the composer as a visibly read-only draft surface.
- Prove the worker’s end-to-end lifecycle and terminal restoration before enabling composer submission.

### Explicitly deferred

- No composer message may steer or queue a goal in P1.
- No command may mutate execution configuration in P1.
- No diff or provider pane is added in P1.
- No token-delta transport is added; the live stream uses completed `TraceEvent` notifications.

### Exit criteria

- A goal can run for at least one multi-round fixture while the UI receives session, model, tool, state, and reviewer events in the same order as `TraceSink`.
- The UI renders current and recent activity without polling away input or losing the transcript tail.
- Scrolling keeps a scrolled transcript stable while new events arrive; End returns to the tail.
- A round-boundary notice and a terminal outcome are delivered exactly once, and a failed worker still restores the terminal.
- A TestBackend live fixture proves `App` alone supplies the activity, status, and read-only composer state.
- The existing replay path remains read-only and its tests remain green.
- Full test, Clippy, and formatting gates pass.

### Ship rule

P1 is shippable as a read-only live monitor. It must not claim mid-run interaction or an interactive diff/provider workspace.

## P2 — Mid-run input, steering, and queued goals

### Purpose

Make the composer operational during a run while preserving the worker’s ownership of orchestration.

### Entry criteria

- P1 exit criteria pass.
- `src/tui/cmd.rs` contains the existing closed `Action` registry, including `Busy`.
- `src/main.rs::run_goal_text` still defines the service/config boundary for between-goal changes.
- `src/engine/orchestrator.rs` has identifiable implementer/reviewer round boundaries.
- The UI has a visible pending state for worker acknowledgements.

### Phase scope

- Enable composer editing and submission while the worker is active.
- Implement `steer` as one pending-steer slot, applied before the next implementer round is assembled.
- Implement `queue` as one pending-goal slot, started only after the current goal reaches a safe boundary and services are rebuilt.
- Route configuration commands through the worker inbox and apply them in submission order at safe round boundaries.
- Acknowledge every mutating command as pending, applied, or rejected; a timeout or worker loss must never imply application.
- Reuse the current `Action` parser and help registry. View-only commands may update `App` immediately, but no view action may mutate the worker outside a boundary.
- Make busy mode, pending steer, pending goal, stopping, and boundary acknowledgement visible in the status/composer chrome.
- Preserve safe quit: the first request arms stopping, the current non-preemptible call finishes, and a second request is handled according to the spec without aborting the worker mid-call.

### Command timing contract

- Help, hotkeys, model/provider listings, and unknown-command feedback are view-only.
- Attempts, rounds, thinking, effort, caps, busy mode, and model/configuration changes are pending until the worker acknowledges a boundary.
- Retry and approval/rejection semantics must be honest: apply only where the current engine has a boundary-safe operation; otherwise keep the existing explicit unavailable response.
- Provider mutation and the `/providers` presentation are completed in P3 after the BYOK dependency gate.

### Exit criteria

- Composer text can be typed, replaced, and submitted during a deterministic in-flight worker fixture.
- Steer text is absent before the boundary and becomes part of the next-round record after the boundary acknowledgement.
- A queued goal is not started twice and receives the configuration visible at its start.
- Commands submitted in order are acknowledged in order; a rejected command leaves execution configuration unchanged.
- Latest-submit replacement and all single-slot clears are visible and tested.
- Graceful stop and terminal teardown pass for normal completion, worker error, and repeated quit requests.
- The existing `tests/tui_app.rs` pattern covers pending/boundary/status states with `TestBackend`.
- Full test, Clippy, and formatting gates pass.

### Ship rule

P2 is shippable only when the UI can prove the timing of every submission. A visually editable composer with hidden or immediate worker mutation does not meet this phase.

## P3 — Transcript, status, diff, providers, and metrics panes

### Purpose

Complete the operational workspace around the live and replay views.

### Entry criteria

- P2 exit criteria pass.
- BYOK provider switching from `docs/superpowers/plans/2026-09-25-byok-providers.md` is merged and green. P3 does not start against a local-only provider prototype.
- `src/tui/auth.rs` keeps provider names/bases separate from 0600 credentials and already exposes verification status.
- `src/engine/orchestrator.rs` owns `TreeService` evidence for the active task.
- `src/tui/render.rs::Counters` already folds model calls, tokens, cost, and review verdicts.

### Phase scope

- Add `/providers` as the display command for built-ins, registry providers, credential presence, and verification status while retaining `/provider add|list|rm` for the existing mutation grammar.
- Apply `/model provider/model` and provider-related changes at the same boundary acknowledgement used by P2, with per-role clients rebuilt before their next use.
- Keep key capture masked and pass secrets directly to `src/tui/auth.rs`; never place key text in generic composer state, transcript lines, traces, or snapshots.
- Add a diff pane fed by a bounded engine-owned diff snapshot. The UI must not run an independent git query that can disagree with the harness’s `TreeService` evidence.
- Add the status metrics pane/row for run state, model/provider, call count, input/output tokens, cost, and review pass/fail. Values must be derived from `App`/trace reducers, not network calls during draw.
- Compose transcript, run, status, diff, provider, and composer panes in wide and narrow layouts.
- Make the same pane composition available to live and replay modes; replay uses recorded/engine evidence and still has no worker or mutating provider actions.

### Exit criteria

- A provider can be added/listed/removed through the existing auth store and displayed through `/providers`; the secret is absent from all rendered output and trace data.
- A role model/provider switch is visibly pending during a run and takes effect only at the acknowledged boundary.
- The diff pane shows the current bounded diff snapshot and an explicit empty/unavailable state; it does not execute git from the draw path.
- Status metrics match the `TraceEvent` fold for a recorded fixture, including cost and review outcomes.
- Wide and narrow TestBackend fixtures show all required panes without overlap, secret leakage, or composer loss.
- Live and replay mode tests exercise the same pane composition; replay remains unable to dispatch commands or create a worker.
- Full test, Clippy, and formatting gates pass.

### Ship rule

P3 is shippable as a complete one-run workspace. A diff or provider view that reads outside the engine/auth boundaries is not an exit.

## P4 — Theme, completion, and safe preference polish

### Purpose

Reduce interaction cost and make the full TUI comfortable for repeated use without expanding its session scope.

### Entry criteria

- P1–P3 exit criteria pass.
- `src/tui/theme.rs` remains the single palette/frame owner.
- `src/tui/cmd.rs` remains the single slash registry and help source.
- The full workspace has stable focus, pane, busy, and replay semantics.
- No phase has introduced transcript, session, credential, or composer persistence.

### Phase scope

- Ship built-in terminal/dark/light theme choices through the existing named-color model, with the selected theme affecting all panes consistently and respecting narrow/replay layouts.
- Add slash-command completion from the existing `Action` registry and provider/model completion from `src/tui/auth.rs` metadata; completion must never expose credential values.
- Persist only non-secret UI preferences in `~/.rof/tui.json`: schema version, selected theme, pane sizes, focus order, and display mode. Use an atomic replacement and ignore/repair malformed preference data without preventing startup.
- Do not persist transcripts, trace paths as session state, composer drafts, pending queues, API keys, or provider secrets.
- Make the current `/display` command reflect the supported fullscreen/regular preference rather than displaying a no-op marker, while preserving the alternate-screen and scrollback contract.
- Add help text for the new `/providers` command, completion behavior, themes, and preference scope.

### Exit criteria

- Theme changes are deterministic in wide, narrow, live, and replay TestBackend fixtures; terminal-default rendering remains compatible.
- Slash completion lists only registered commands and provider/model completion never reveals keys or mutates configuration.
- A valid `~/.rof/tui.json` round-trips theme, pane sizes, focus order, and display mode; malformed data falls back safely.
- Restarting `rof chat` restores only the allowed preferences and does not restore a run, goal, transcript, queue, or secret.
- Full test, Clippy, and formatting gates pass.

### Ship rule

P4 is polish with a hard data-safety boundary. Any persistence request outside the allowlist is a new product decision, not an implicit P4 extension.

## Cross-phase acceptance

The full-TUI vision is accepted only when all four phases have independently passed their exit criteria and the following end-to-end checks pass:

1. A single live goal runs on a worker future while the user can scroll, inspect activity, submit steer text, queue one next goal, and see every command’s boundary result.
2. Configuration changes and provider/model changes do not affect the current call and do not apply silently after a rejection.
3. The wide and narrow workspaces show transcript, run, status, diff, provider, and composer information sourced from `App`.
4. BYOK key capture is masked and no key appears in traces, logs, replay lines, completion output, or preferences.
5. A recorded JSONL trace reopens in seekable replay, filters lines, and cannot run a goal or dispatch a command.
6. Existing `run`, `eval`, auth, command, and TUI suites remain green; formatting and Clippy warnings-denied checks pass.

## Risks and mitigations

- **Event ordering drift:** use one emission seam and test live order against `TraceSink` order.
- **Configuration races:** keep the UI-to-worker inbox boundary-only and require visible acknowledgements.
- **Secret leakage:** keep key capture outside generic notification state and test rendered buffers for absence.
- **Diff disagreement:** use engine-owned bounded snapshots, not UI-side git.
- **Event snapshot cost:** replace live polling with the channel while retaining bounded `App` collections; do not repeatedly clone the whole trace during an active run.
- **Terminal lifecycle loss:** keep raw-mode/alternate-screen restoration on normal completion, worker error, channel closure, and repeated quit paths.
- **Scope creep:** reject token deltas, session persistence, remote attachment, and multi-session work as separate decisions.

## Definition of done

The plan is complete when the four phase gates are independently evidenced, the cross-phase acceptance checks pass, no phase has added a prohibited dependency or data-retention behavior, and the implementation remains compatible with the existing `rof run`, `rof eval`, provider, and replay paths.
